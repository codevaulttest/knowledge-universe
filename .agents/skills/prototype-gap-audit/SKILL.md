# 原型待办盘点

## 铁律：待办的来源

用户的待办**只能**来自两处：
1. **`raw_context/`** —— 会议转写 + 群聊导出，是团队真实拍板过的需求。这是主干。
2. **用户当面说的产品意图** —— 用户脑子里默认要、但没在群里打字的（如 bio、图片放大）。

**禁止**拿"一个成熟社交产品标准该有什么"的外部模板当待办来源。那样会无中生有一堆没人要过的伪需求（@提及、表情选择器、话题标签……），污染真实 backlog。这是本 skill 最容易犯、也最该避免的错。

外部功能清单**唯一**的正当用途见下方第 3 步：当作勾用户记忆的**提问单**，逐条问、用户点头才算数——永远不能直接列成"缺口/待办"。

## 三步法

### 第 1 步：穷尽扫 raw_context（主干）

不要只看最近几天的聊天——那会漏掉没被反复提起的老需求（这是之前翻车的根因）。对**全部** `raw_context/`（含 `chat-export/*/result.json` 的历史群聊、所有 `Record_*` 转写、`*.md` PRD）做需求抽取：

```bash
# 把群聊 JSON 拍平成可搜的文本，逐主题 grep
for d in raw_context/chat-export/ChatExport_*; do
  python3 -c "import json,sys
for m in json.load(open('$d/result.json')).get('messages',[]):
    t=m.get('text','');
    t=''.join(x if isinstance(x,str) else x.get('text','') for x in t) if isinstance(t,list) else t
    if t.strip(): print(m.get('from'),':',t.replace(chr(10),' '))"
done > /tmp/all-chat.txt
grep -niE '认证|举报|简介|评论|盖楼|频道|订阅|…' /tmp/all-chat.txt
```

每抽到一条需求，记录**出处**（谁、哪天说的），再去代码里判断做没做。

### 第 2 步：代码现状核验（辨真伪，别跳过）

对每条需求打开对应文件确认真实状态。**代码里有字符串 ≠ 功能做了**：
- 无关变量名的巧合（搜 `bio` 命中的可能是 `tiersSignature`）
- 数据结构里有字段、但没有 UI 入口（`description` 是频道的、不是用户 bio）
- 只做了一半（认证只有单一蓝V，缺"官方/客服/明星"分类——而这个分类是 raw_context 08-07 明确要过的）

页面清单与项目约定见 `references/social-feature-checklist.md`。

### 第 3 步：候选提问（可选，必须与待办分开）

`raw_context` 抓不到用户脑子里的隐性需求（bio、图片放大就是例子——聊天里零痕迹）。此时可用 `references/social-feature-checklist.md` 的标准功能清单，**当作提问单**逐条勾用户记忆：

> "以下这些标准功能当前没做，你们要不要排：删除自己评论 / @提及 / 表情选择器 …？"

规则：
- 这些**不是**待办，是**问题**。只有用户回"要"才升级成待办。
- 输出里必须单独成节，标题写"待你确认（候选，raw_context 无据）"，**绝不**混进"确认待办"表格。

## 输出格式

分两块，永不混淆：

**一、确认待办（有据）** —— 每条都能指到 raw_context 出处或用户原话：

| 功能 | 现状(❌/⚠️部分) | 出处（谁·哪天） | 建议优先级 |
|---|---|---|---|

**二、待你确认（候选，无据）** —— 标准功能里缺的，列成问题请用户拍板，不预设是待办。

定级按 ROI × 紧急度：P0 快/止损、P1 独立可做、P2 大/下一阶段/牵扯规则（继承自 raw_context 里领导已说"后续"的判断）。
